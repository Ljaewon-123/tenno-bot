# 디스코드 임베드 규격서

teno-bot 슬래시 커맨드 출력을 디자인할 때의 제약 명세. discord.js 14.26.4 기준.

디스코드 메시지는 자유 캔버스가 아니라 **고정된 슬롯 목록**이다. 이 문서 밖의 것을 그리면 코드로 옮길 때 버려진다.

## 원칙 — 픽셀이 아니라 슬롯을 디자인한다

디자인이 바꿀 수 있는 건 **무엇을 어느 슬롯에 넣고, 어떤 순서로, 어떤 위계로 쓰느냐**다.
여백·정렬·폰트·박스는 디스코드 클라이언트가 정하며 봇이 건드릴 수 없다.
그래서 좋은 임베드 디자인은 타이포그래피가 아니라 **편집**에 가깝다 — 무엇을 자르고, 무엇을 접고, 무엇을 한 줄로 합치는가.

목업을 그린다면 반드시 실제 렌더 폭·색·행간으로 그린다. 예쁘게 보이려고 폭을 늘리거나 여백을 키우면, 옮겼을 때 전혀 다른 물건이 된다.

## 렌더 모드는 둘 중 하나만

| | 임베드 (Embed) | 컨테이너 (Components V2) |
|---|---|---|
| 생김새 | 좌측 4px 색 바 + 제목/본문/필드 격자 | 블록을 위에서 아래로 쌓음 |
| 강점 | 정보 나열, 3열 격자 | 구분선·섹션·버튼 혼용, 위계 표현 |
| 3열 격자 | `inline: true` 로 가능 | **없음** — 세로 스택만 |
| 이미지 | 썸네일(80px) + 큰 이미지 슬롯 | Section 우측 액세서리, MediaGallery |
| 버튼 | 없음 | 있음 |
| 제약 | 메시지당 10개까지 | 플래그를 켜면 `content`·`embeds` 동시 사용 불가 |

한 메시지 안에서 둘을 섞을 수 없다. 커맨드 하나당 모드를 정하고 그 안에서 디자인한다.
컨테이너 예시는 [`src/party/party-message.service.ts`](../src/party/party-message.service.ts).

## 변환 가능성

### 코드로 옮겨진다

- 마크다운 위계 — `###` 제목, `**굵게**`, `-#` 작은 회색 글씨, `>` 인용, 리스트
- 정보의 순서, 묶음, 줄바꿈 위치
- 필드 분할과 `inline` 3열 격자 배치
- accent color (임베드 좌측 바 / 컨테이너 테두리)
- 이모지·커스텀 이모지를 아이콘 대용으로
- 썸네일 · 큰 이미지 · footer · author 슬롯 사용 여부
- 상대 시각 표기 `<t:unix:R>`, 멘션, 링크
- 컨테이너: 구분선 위치와 간격, 섹션 우측 액세서리, 버튼 행
- 코드블록 · ` ```ansi ` 블록 (색 있는 글자를 쓰는 유일한 방법)

### 표현 수단이 아예 없다

- 폰트, 글자 크기, 자간, 줄간격
- 여백 · 패딩 · 요소 간 간격
- 배경색, 카드, 테두리, 그림자, 모서리 반경
- 가운데·우측 정렬
- 표(table), 컬럼 폭 지정
- 본문 중간 이미지 삽입 — 이미지는 정해진 슬롯에만
- 아이콘 위치 지정, 진행바·차트·배지 그래픽
- 2열 이상 자유 레이아웃 (임베드 3열 격자 외)
- hover·애니메이션·상태 전환

> 아래 것이 정말 필요하면 방법은 하나다 — 이미지를 직접 그려 첨부하는 것. 매 호출마다 렌더링 비용이 붙으므로 정말 필요할 때만.

## 규격 · 임베드

| 슬롯 | 한도 | 렌더 | 주의 |
|---|---|---|---|
| `title` | 256자 | 16px 굵게 | 마크다운 안 먹음. 링크는 `setURL()`로 제목 전체만 |
| `description` | 4096자 | 16px 본문 | 마크다운 전부 사용 가능 |
| `fields` | 25개 | 세로 또는 3열 | `inline: true`가 연속 3개 모이면 한 줄 |
| `field.name` | 256자 | 14px 굵게 | **마크다운·링크 안 먹음.** 이모지는 됨 |
| `field.value` | 1024자 | 14px | 마크다운 전부 사용 가능 |
| `footer.text` | 2048자 | 12px 회색 | 마크다운 안 먹음 |
| `author.name` | 256자 | 14px 굵게 | 아이콘은 24px 고정 — 키울 수 없다 |
| `thumbnail` | 80×80 | 우상단 | 원본이 커도 80px로 줄어든다 |
| `image` | 폭 ~400px | 하단 전체 | 상한 아래면 원본 크기 그대로 — 큰 이미지는 임베드를 잡아먹는다 |
| 전체 합 | 6000자 | — | 위 슬롯 문자 수 총합. 메시지당 임베드 10개 |

한도를 넘기면 디스코드가 400을 뱉고 메시지가 아예 안 나간다.
코드에서는 항상 `.slice()`로 자르지만, 디자인 단계에서 **필드 하나에 1024자를 넘길 구성을 애초에 만들지 않는 것**이 맞다.

## 규격 · Components V2

| 부품 | 담는 것 | 한도 | 쓰임 |
|---|---|---|---|
| `Container` | 아래 부품들 | — | accent color를 가진 바깥 상자 |
| `TextDisplay` | 마크다운 텍스트 | 메시지 합 4000자 | 본문 전부. 제목도 `###`으로 여기서 |
| `Section` | TextDisplay + 액세서리 1 | 1–3 | 우측에 썸네일이나 버튼 하나를 붙일 때 |
| `Separator` | — | — | 구분선 on/off, 간격 small · large |
| `MediaGallery` | 이미지 항목 | 1–10 | 이미지 여러 장을 격자로 |
| `ActionRow` | 버튼 | 5개 | 버튼 행 |
| 메시지 전체 | 모든 컴포넌트 | 40개 | 중첩까지 합산 |

Section의 1–3, MediaGallery의 1–10은 설치된 `@discordjs/builders`가 직접 검증한다. 나머지 총량 한도는 서버가 거절하는 값이다.

## 마크다운 지원 범위

| 문법 | 결과 | `description` / `field.value` / `TextDisplay` | `title` · `field.name` · `footer` |
|---|---|---|---|
| `#` `##` `###` | 제목 3단계 | 먹음 | 안 먹음 |
| `-# 텍스트` | 작은 회색 글씨 | 먹음 | 안 먹음 |
| `**굵게**` `*기울임*` | 강조 | 먹음 | 안 먹음 |
| `> 인용` | 좌측 세로선 | 먹음 | 안 먹음 |
| `- 리스트` / `1.` | 목록, 들여쓰기 가능 | 먹음 | 안 먹음 |
| `[텍스트](url)` | 링크 | 먹음 | 안 먹음 |
| `` `코드` `` / 코드블록 | 고정폭 · 회색 배경 | 먹음 | 안 먹음 |
| `\|\|스포일러\|\|` | 가림막 | 먹음 | 안 먹음 |
| `<t:unix:R>` | 뷰어 로컬 시각 · 상대 표기 | 먹음 | 안 먹음 |
| 😀 `<:name:id>` | 이모지 · 커스텀 이모지 | 먹음 | **먹음** |

필드 이름에서 유일하게 쓸 수 있는 시각 장치가 이모지다. 아이콘이 필요하면 여기로 넣는다.
`<t:>`는 뷰어 시간대로 자동 변환되므로 "3시간 뒤" 같은 문구를 직접 쓰지 않는다.

## 목업을 그린다면 이 값으로

| 항목 | 값 |
|---|---|
| 임베드 폭 | 516px 고정 (데스크톱 기준) |
| 채널 배경 / 임베드 배경 | `#313338` / `#2b2d31` |
| 본문 / 제목 / 흐린 글씨 | `#dbdee1` / `#f2f3f5` / `#949ba4` |
| 링크 | `#00a8fc` |
| accent bar | 4px, 현재 값 `#5865f2` |
| 임베드 안쪽 여백 | 16px, 모서리 4px |
| 본문 / 필드 이름 / 필드 값 / `-#` | 16px · 14px 600 · 14px · 12.8px |
| 행간 | 1.375 |
| 폰트 | gg sans → Noto Sans 대체 |
| 블록 사이 간격 | 8px |

근사값이다. 실제 렌더는 클라이언트·창 너비·모바일 여부에 따라 달라진다.
모바일에서는 3열 격자가 1열로 무너진다는 것만 기억하면 된다.

## 넘기기 전 자가 점검

1. 임베드 폭이 516px 고정인가? 늘리지 않았는가
2. 배경 박스·테두리·그림자를 새로 그리지 않았는가
3. 모든 텍스트가 마크다운으로 표현 가능한가 (크기·색·정렬 지정 없음)
4. 필드 이름에 굵게·링크를 쓰지 않았는가 (이모지만 허용)
5. 필드 값이 1024자, 필드 수가 25개 안에 들어오는가
6. 3열 격자를 썼다면 모바일 1열로 무너져도 읽히는가
7. 이미지는 썸네일(80px)·큰 이미지 슬롯에만 있는가
8. 시각 표기는 `<t:>`인가 (직접 쓴 "3시간 뒤"가 아닌가)
9. 임베드안과 컨테이너안을 섞지 않고 하나만 골랐는가

## 출력 원형 — 커맨드별로 새로 디자인하지 않는다

커맨드는 10개가 넘지만 출력의 모양은 네 가지뿐이다. 원형을 먼저 정하고 커맨드는 거기에 데이터를 끼운다.

| 원형 | 모양 | 해당 커맨드 |
|---|---|---|
| **A. 단일 이벤트** | 제목 + 상태 한 줄 + 만료 + 세부 3~4줄. 이미지 슬롯 사용 | `/archon-hunt` `/sortie` `/void-trader` |
| **B. 그룹 목록** | 헤더로 묶인 항목 나열. 개수 가변, 길면 잘림 | `/void-fissures`(티어 6그룹) `/nightwave`(일일·주간·엘리트) `/archimedea`(심층·시간) `/drop`(아이템별) `/events` |
| **C. 상태 타일** | 짧은 상태 여러 개를 `inline` 3열로 | `/cycles` |
| **D. 관리 목록** | 내가 등록한 것 조회. 조작 대상이라 식별자가 보여야 함 | `/alarm list` `/notification list` `/party list` |

`/party create`는 버튼이 붙는 상호작용 메시지라 원형 밖이다 — 이미 컨테이너로 구현돼 있다.

### 원형과 별개로 한 번만 정하면 되는 것

정해두면 모든 커맨드에 그대로 적용된다. 커맨드마다 다르게 가면 봇이 산만해진다.

1. **만료·남은 시간** — `<t:unix:R>`을 어디에 두나 (description / 첫 필드 / footer), 문구는 무엇으로 통일하나
2. **accent color** — 전 커맨드 통일(현재 `#5865f2`)인가, 카테고리별로 나누나
3. **이모지 아이콘** — 쓸 것인가. 쓴다면 필드 이름 앞 1개 같은 규칙으로 고정
4. **배지 표기** — 하드/강철 같은 표시를 `(hard)` `[Steel Path]` 중 무엇으로 통일하나
5. **빈 상태** — "No active events currently." 형식의 문구를 어떻게 통일하나
6. **잘림 규칙** — 목록이 한도를 넘길 때 몇 개까지 보이고 나머지를 어떻게 알리나 (`+N more`)
7. **언어** — 유저에게 나가는 문자열은 영어 (CLAUDE.md 규칙). 필드 이름·설명 모두

### 목업으로 받아야 할 것

커맨드 10장이 아니라 **원형 4장 + 공통 요소 1장**. 원형은 실제 데이터가 가장 빡빡한 케이스로 그린다 — B는 `/void-fissures`(티어 6개, 항목 수십 개)나 `/archimedea`(2종 × 미션 3 + 수정자 4), A는 `/void-trader`(재고 목록 + 이미지).

---

확정은 목업이 아니라 실제 렌더로 한다 — 고른 안을 코드로 옮겨 테스트 채널에 띄우고 스크린샷으로 한 번 더 본다. 목업은 "안 고르기"까지만 담당한다.
